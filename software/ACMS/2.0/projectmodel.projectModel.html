projectmodel.projectModel module

projectModel module

Created on Wed Apr 5 15:04:38 2023

This module (more in general this package) allows to externalize data modelling with respect to the real Physical Component’s representation.

At the time of writing this code (and documentation) there are no clear requirements about the data modelling and how the data must be treated and used in the future; thus the programmer took advantage for foreseeing a whole “spectra” of possible models, in case to be written in this package.

The only clear requirements we have (for now) are:

1- It must be possible to “group” different instances of controllers (regardless of their type) based on the Plant System functionalities.

2- It must be possible to “arrange” the software objects in a hierarchycal structure.

Given these two constraints the Projectmodel class have been implemented as follows.

class projectmodel.projectModel.projectmodel(settings)[source]

Bases: object

The project model is the way the information is organized

Currently the Smart Controller’s can be grouped by “Plant System Functionlity” and can be (if needed) organized in a hierachycal structure, based on parent-child relationship.

One important pre-requisite is that the Controller Instances’s names are unique.

In the current implementation of the ProjecModel the dictionary called _registered_groups contains the information about how the Controllers must be divided into Functional Groups while the dictionary _registered_nodes contains all the “nodes” objects with connection capabilities in order to be arranged in a hierarchycal structure.

By design the node objects are different from the Instances objects but they duplicates the latters; this choice of keeping separated the two software entities is mainly due to the lack of visibility about how this software will be used in the near future, having the software entities separated allow a separate development and assures (at the same time) to always recall a Controller Instance by its name based on the Model needs.

adds and instance node to its parent

If the node corresponding to the current_instance does not exist, the method creates it.

In any case the method attaches the Instance’s node to the specified parent.

Parameters:

  • current_instance – The controller’s Instance (software object)

  • parent_node – the name of the parent node (equal to the name of the parent controller)

add_node(current_instance)[source]

This method is responsible for assembling the attributes dictionaries _registered_nodes and _registered_groups

it first registers the group to which each controller instance belongs to, below each group it adds the instance name (just the name, it is unique); then it tries to retrieve the “parent” controller object, if the parent is not found or it is unspecified, the method registers the node and attaches it to the root node (_model). If the current instance does not exist as registered node the method creates a new node object with the same name of the current controller’s instance.

If the node already exist (for example because it was previously created in quality of parent of another node) the method simply assignes to it the proper parent (if different from _model) and marks it as processed (attribute processed = True).

The processed attribute will be used for checking possible anomalies.

The so implemented logic is able to build a complex hierarchycal tree regardless of the order of declaration of the nodes.

Parameters:

current_instance – the current Controller’s Instance (as returned by instances_factories)
